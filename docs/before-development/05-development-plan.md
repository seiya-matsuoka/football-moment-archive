# Football Moment Archive 開発計画

## 1. 文書概要

### 1.1 目的

本書は、`football-moment-archive` の実装順序、各工程の実施内容、確認方法、完了条件、Git・GitHub 上の作業単位を定義するための文書である。  
本書は開発中の進行判断と作業管理の基準として使用する。

### 1.2 対象範囲

本書では、次の内容を対象とする。

- 開発の目的
- 開発方針
- 開発対象と完成条件
- 使用技術・開発環境
- 実装工程
- 各工程の確認方法

画面仕様は `screen-design.md`、データ構造は `data-design.md`、アプリケーション構成は `architecture.md` で定義する。  
本書では、各設計の詳細を重複して記載せず、どの順序で実装し、何を確認したうえで次の工程へ進むかを中心に扱う。

## 2. 開発の目的

本開発では、Next.js App Router を使用した小規模なフルスタック Web アプリケーションを完成させる。  
Server Component、Server Action、Data Access Layer、PostgreSQL 接続、動的ルート、URL 検索パラメーター、状態画面など、Next.js による基本的なアプリケーション開発の流れを一通り経験する。

実装範囲を必要以上に広げず、試合と場面の登録・参照・編集・削除を中心とした完成可能な構成とする。  
認証、複雑な権限管理、外部 API 連携、高度な検索基盤などは導入せず、確定済みの要件を最後まで実装することを優先する。

## 3. 開発方針

- DB 接続とテーブルを最初に準備する
- 試合機能を先に実装し、その後に場面機能を実装する
- 参照機能を先に実装し、表示内容を確認してから更新機能を追加する
- 基本的な CRUD を完成させてから、検索・絞り込み・並び替え・ページネーションを追加する
- 各工程を小さな単位で完成させ、次の工程へ進む前に動作確認する
- 画面、サーバー処理、DB の 3 方向から確認する
- Server Component を基本とし、Client Component は必要な操作に限定する
- SQL は Data Access Layer に集約する
- 実装中に不要なレイヤーやライブラリを追加しない
- 自動テストは初期開発の対象外とし、手動確認と品質確認コマンドを使用する
- デプロイは主要機能と最終確認が完了した後に行う
- 実装時に確定設計から変更する場合は、理由と影響範囲を確認してから反映する

## 21. Git・GitHub の運用方針

### 21.1 基本フロー

```text
Issue を作成
  ↓
feature ブランチを作成
  ↓
実装
  ↓
動作確認
  ↓
品質確認
  ↓
Pull Request を作成
  ↓
内容確認
  ↓
Squash and merge
  ↓
main を更新
```

### 21.2 ブランチ

- `main` は完成済みの変更だけを保持する
- 1 つの Issue に対して 1 つの feature ブランチを基本とする
- 異なる目的の変更を同じブランチへ混在させない
- 実装中に別の問題を発見した場合は、現在の Issue に含める必要性を判断する
- スコープ外の変更は別 Issue として扱う

### 21.3 コミット

日本語の Conventional Commits を使用する。

例：

```text
feat: 試合一覧の表示を追加
feat: 場面登録処理を追加
fix: 試合日の未入力時の並び順を修正
refactor: 場面データの変換処理を整理
docs: 開発計画を追加
style: フォームの余白を調整
chore: Prettier の設定を追加
```

1 コミットには、内容を説明できるまとまりの変更を含める。  
作業途中の状態を無理に細かく分割せず、変更目的を把握できる単位とする。

### 21.4 Pull Request

Pull Request には、次の内容を記載する。

- 変更目的
- 主な実装内容
- 確認内容
- 関連する Issue
- 補足事項

大規模な説明テンプレートは使用せず、変更内容を確認するために必要な情報へ絞る。

### 21.5 Merge

Pull Request は Squash and merge を使用する。  
マージ後は不要になった feature ブランチを削除する。

## 22. Issue・ブランチ・Pull Request の分割方針

### 22.1 基本単位

次の単位を Issue と Pull Request の候補とする。

1. プロジェクト初期設定
2. DB 環境・テーブル・シードデータ
3. 共通基盤
4. 試合の参照機能
5. 試合の登録・編集・削除機能
6. 場面の参照機能
7. 場面の登録・編集・削除・お気に入り機能
8. 一覧の検索・絞り込み・並び替え・ページネーション
9. ホーム・状態画面・Metadata
10. UI・レスポンシブ・アクセシビリティ調整
11. 全体確認・仕上げ
12. デプロイ

### 22.2 分割判断

1 つの Issue が大きくなり、確認対象や完了条件が不明確になる場合は分割する。  
一方、変更量が少なく相互依存が強い内容は、無理に細分化しない。

分割例：

```text
試合の登録・編集・削除機能
  ↓
試合登録・編集
試合削除
```

```text
一覧機能
  ↓
試合一覧の検索・ページネーション
場面一覧の検索・ページネーション
```

実際の Issue 名、ブランチ名、Pull Request 名は、各工程を開始する時点で決定する。

## 23. 実装中の変更管理

### 23.1 設計変更

実装中に設計変更が必要になった場合は、次の内容を確認する。

- 変更が必要な理由
- 既存要件への影響
- DB への影響
- 画面への影響
- アーキテクチャへの影響
- 既存データへの影響
- 現在の Issue に含めるか
- 別 Issue とするか

### 23.2 ドキュメント更新

確定済みの要件や設計を変更した場合は、関連する開発前ドキュメントへ変更内容を反映する。  
実装上の細かな差分や完成後に確定した内容は、実装完了後の設計書へ反映する。

### 23.3 スコープ追加

次の条件を満たさない機能は、開発中に追加しない。

- 現在の要件を満たすために必要
- 実装しないと主要機能が成立しない
- 既存設計との整合性を保てる
- 開発規模を大きく増やさない

「あると便利」「実務では使用される」「将来必要になる可能性がある」という理由だけでは追加しない。

### 23.4 不具合

現在の工程で実装した機能の不具合は、原則として次の工程へ進む前に修正する。  
既存工程に影響しない軽微な UI 調整は、UI 調整工程へまとめてもよい。
